# 消息队列化与 Steering（运行中插话 / btw）

> 状态：设计已确认，待实现。
> 关联：依赖 pi-agent-core 的 `getSteeringMessages` / `getFollowUpMessages` 钩子；复用现有 EventBus、canonical 落盘、UserMessageCard。

## 1. 背景与目标

当前 agent 运行中（`loading`），`useAgent.submit` 直接 `return`，用户无法插话。目标：

- 允许用户在 agent 运行中继续发消息；该消息以 **QUEUED** 态展示，待合适时机注入 loop 供 agent 据此调整（"纠偏 / btw"）。
- 消息最终要**落入 history.jsonl**。
- 切换会话 / 退出窗口 / 中止时，**防止残留消息被下一轮静默注入**，也**防止重发导致重复消费**。

## 2. 核心设计

**一个队列 + 两个排空钩子 + 结束兜底清理。**

- **单一 steering 队列**：运行中用户发的消息入队。
- **`getSteeringMessages`**：pi 在「run 开始」和「每个 turn 结束、下次调 LLM 前」排空队列 → **运行中纠偏**，中途注入。
- **`getFollowUpMessages`**：pi 在「agent 即将退出前」排空队列 → **兜住"极晚窗口"**（消息恰好卡在最后一次 steering 排空之后才入队）。
- **run 结束 clear**：`prompt()` 里 `loop.run()` 返回后清空队列（`try/finally`）。正常流程队列早被排空，此步是 no-op；只在**中止/报错**等异常路径真正生效，清掉未消费消息，防止被下一轮 run-start 的 steering 静默注入。

pi 注入的消息会 push 进 loop 返回的消息序列，Vivlos 的 canonical 落盘自动带上，**无需也不应手动写 history**（手动写会重复）。

### 消息卡片三态

| 状态 | 含义 | 左上角字样 | 左边框色 | 触发 |
|---|---|---|---|---|
| 正常态 | 已发送并被处理 | 无 | 正常紫 `#cba6f7` | QUEUED 被注入后 |
| QUEUED | 已发送、待处理 | `QUEUED` | 橙色 | 运行中发送瞬间 |
| 未发送 | 因故未发给 llm | `未发送` | 黄色 | run 中止/报错且未被排空 |

状态流转：

```
用户运行中发送 → QUEUED(橙)
   ├─ steering/followUp 注入 → 正常态
   └─ run 中止/报错且未注入 → 未发送(黄)
```

## 3. 数据模型与事件

### 3.1 SteeringQueue（新模块 `vivlos/agent/steering/queue.ts`）

队列元素带 id，便于 TUI 精确翻转卡片状态：

```ts
interface QueuedMessage { id: string; message: AgentMessage; }

interface SteeringQueue {
  /** 入队并去重；返回 { id, deduplicated }。相同文本且未消费 → 复用已有 id，不新建 */
  push(text: string): { id: string; deduplicated: boolean };
  /** 排空并返回 AgentMessage[]（供 pi 钩子）；对被消费的 id 发 steering:consumed */
  drain(): AgentMessage[];
  /** 清空（run 结束兜底）；对被丢弃的 id 发 steering:dropped */
  clear(): void;
}
```

- `push` 去重：与"当前仍在队列中（未消费）"的消息比对文本，相同则复用其 id，`deduplicated=true`。
- `drain` 由 `getSteeringMessages` 与 `getFollowUpMessages` 共用。
- 依赖注入 `eventBus` 用于发消费/丢弃事件。

### 3.2 新增事件（`infra/eventbus/events/`，并入 VivlosEvent）

```ts
| { type: "steering:consumed"; sessionId: string; ids: string[] }   // 被注入
| { type: "steering:dropped";  sessionId: string; ids: string[] }   // 被清空丢弃
```

### 3.3 LogEntry 新增 `user` 类型（`useAgent.ts`）

QUEUED/未发送卡片作为"用户消息条目"插入当前轮 log：

```ts
| {
    kind: "user";
    queuedId: string;        // 对应 SteeringQueue 的 id
    text: string;
    state: "queued" | "unsent" | "normal";  // queued→(注入)normal / (丢弃)unsent
    turnIndex: number;
    createdAt: number;
  }
```

> 注：正常态的用户消息不进 log（仍由 turn 的 `userInput` 承载）；此条目只承载"运行中插话"的瞬态卡片。

## 5. 关键流程

### 5.1 运行中插话并被处理（主路径）
1. agent 运行中，用户发送 B → `submit` 检测 `loading` → `agent.queueMessage(B)` → 队列 push（得 id）→ TUI 追加 `user` LogEntry（QUEUED 橙）。
2. pi 到下一个 turn 边界 → `getSteeringMessages` drain → B 注入上下文 → 发 `steering:consumed:[id]`。
3. TUI 收到 consumed → 该条目 QUEUED 消除（转正常/移除，见 6.2）。
4. agent 回应 B；run 结束 → B 随 canonical 落 history。

### 5.2 极晚窗口（followUp 兜底）
- B 恰好卡在最后一次 steering 排空之后入队 → steering 没排到 → run 即将退出时 `getFollowUpMessages` drain → B 注入，agent 补一轮回应 → 落 history。正常 run 下消息必被处理。

### 5.3 中止 / 报错
- run 异常退出（未走 followUp）→ B 未被排空 → `prompt()` finally 里 `queue.clear()` → 发 `steering:dropped:[id]` → TUI 把条目转"未发送"（黄）。B 不落 history。用户可重发（重发是全新消息）。

### 5.4 去重
- B 仍在队列（QUEUED）时再发相同内容 → `push` 返回已有 id、`deduplicated=true` → TUI 不新建卡片。只有真正因中止/报错被丢弃的才转"未发送"。

## 6. UI 渲染

### 6.1 插入位置
- 用户一发送就**追加 `user` 条目到当前轮 log 末尾**；后续 agent 产出的条目继续往后追加，卡片即停在"发送那一刻"的位置（如 `thinking → calling → [卡片] → text`）。
- **不打断其他条目流式**：仅追加数组，正在流式的 text/thinking 照常刷新。

### 6.2 注入后的呈现（已定：方案乙）
- **方案乙（采用）**：注入后条目**原地转为"正常态用户卡片"**保留。live 视图里该消息始终可见，agent 回应紧随其后。
- 不采用"移除"（方案甲）：会让用户消息在 live 视图凭空消失。
- **不重复渲染保证**：TUI 不订阅 `agent:message_start`，注入的 user 消息不会由事件再渲染一张；重载时 `messagesToTurns` 从 transcript 重建（瞬态 log 已不在），也只显示一份。两视图各一份、不叠加。

### 6.3 配色
- QUEUED：橙（字样 + 左边框）。未发送：黄（字样 + 左边框）。正常态：现有紫 `#cba6f7`。具体色值实现时从主题取（橙/黄需与现有 Catppuccin 调色一致，如 `#fab387`/`#f9e2af`）。

## 7. 持久化与 history

- **只有被注入（走到正常态）才落 history**，且由 canonical 自动完成。
- 未发送（被 clear 丢弃）**不落 history**：黄色卡片仅存在于当前会话 UI，重载后消失（符合"没发出去"语义）。
- 重载重建（`messagesToTurns`）时，被注入的消息作为正常 user 消息出现（可能独立成轮）——与运行中的"内联卡片"视觉略有差异，属可接受的最终态。

## 8. 边界与兜底

| 情况 | 处理 |
|---|---|
| 运行中插话 | steering 中途注入 |
| 极晚入队 | followUp 退出前注入 |
| 中止/报错 | clear 丢弃 → 未发送(黄) |
| 切会话 | 队列随 run 结束 clear；per-session 隔离 |
| 退出窗口/进程 | 内存队列随进程消失，未注入不落盘 |
| 重复发送 | push 去重，不新建卡片 |

## 9. 测试要点

- SteeringQueue：push/drain/clear 语义、去重命中/不命中、consumed/dropped 事件触发与 id 正确。
- 钩子接线：`getSteeringMessages`/`getFollowUpMessages` 均能 drain 同一队列。
- `prompt()` 结束 clear：正常（no-op）与异常（丢弃并发事件）。
- TUI：QUEUED → 正常 / QUEUED → 未发送 两条翻转路径；插入位置正确；不重复渲染。
- 集成：运行中插话 → 被注入 → 落 history（可借 faux provider 验证消息进入 canonical）。

## 10. 风险 / 待验证

1. **pi 注入消息是否确进 canonical**：已在 pi 源码确认注入消息 push 进 `newMessages`（loop 返回值），Vivlos 从 loop 结果落盘——实现后用集成测试锁定。
2. **6.2 注入后呈现**（甲/乙）以实现时"不重复渲染"为准。
3. **followUp 多走一轮**：晚到消息会让 run 多跑一轮回应，属期望行为。
4. 橙色/黄色从主题取，避免硬编码漂移。
